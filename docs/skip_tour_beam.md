# Skip Tour Beam Search

[編集用テンプレート](../src/lib/search/skip_tour_beam.nim) / [探索エンジン](../src/lib/search/skip_tour_beam_core.nim) / [基本例](../src/examples/skip_tour_beam/basic.nim) / [AHC021例](../src/examples/skip_tour_beam/ahc021.nim)

`skipTourBeam`は、世代スキップを扱う独立した差分更新ビームサーチ。
1ターン遷移専用の[tourBeam](tour_beam.md)とは、経路管理・巡回・探索ループを分けて持つ。
候補型・Hash表・セグ木選抜・グループ選抜・葉情報復元・経路コピーは
[共通実装](../src/lib/search/tour_beam_common.nim)を両coreからincludeする。
skipTour専用の遅延確保はコンパイル時に切り替え、実行時の方式判定は増やさない。
親・兄弟リンク型の[skipBeam](skip_beam.md)には依存せず、ユーザーのAPIも変わらない。
固定ビーム幅で動作し、時間計測・時間による打ち切り・可変幅は持たない。

## 方式

Stateは1つだけ保持する。木の辺に相当するActionと、その辺を進む・戻るオイラーツアーを連続配列で保持する。
将来世代の選抜器が参照する親は、展開せずに経路だけ残す。現在世代で選ばれた子だけを適用して展開する。

世代を進める際は、現在の候補と将来候補の親を印付けし、ツアーを走査して必要な祖先を求める。
不要な枝を除去して配列を詰め、親番号をまとめて更新する。祖先ごとの参照数更新や親・兄弟リンクの付け替えは行わない。
全経路に共通する先頭は接頭辞の配列へ分離する。Stateは最後に展開した葉の位置に保持し、世代末に根へ戻さない。
保持するActionの連続区間は`supportsCopyMem(Action)`がtrueなら一括コピーし、参照管理が必要な型では通常代入する。

候補は親の配列位置ごとに計数整列する。旧ツアーを逆から読み、前世代の末尾に近い枝から次世代を展開する。
同じ親から追加する子は選抜スロット順。次のツアーもこの巡回順で作るため、世代ごとに巡回方向が反転する。
待機経路の走査ではStateを動かさず、実際に候補を展開する時だけ、前の位置から必要な共通祖先へ戻って差分を適用する。
現在地のAction列と、親番号変換表で更新する経路位置を保持するので、現在地の枝が配列から消えても巻き戻しに必要な情報は残る。
候補がない空の世代では、適用も巻き戻しも行わない。
空世代では経路の再構築・親番号更新も省略し、次の非空の到着時刻まで選抜器を進める。
省略した世代数が奇数なら、次の展開前に入退場イベントを反転し、従来の巡回方向を保つ。
Hash表・候補領域は最初の通常候補登録時、グループ保留領域は最初の群候補登録時に確保する。
使用済み領域は選抜器ごとに再利用し、中間の未使用世代には幅相応の領域を確保しない。
Stateと経路IDの一致確認済みの確定接頭辞長を保持し、先頭からの再比較・ID再書込みを省く。
新しく接頭辞へ昇格した部分は一致を確認し、必要ならStateを巻き戻して適用する。
現在世代の候補を取り出したあと、未来の選抜器に候補が残っていない層では専用経路を使う。
親の印付け・祖先への伝播・ツアーのフィルタ処理を省き、旧ツアーを1回巡回して採用枝だけを残す。
全候補が`step=1`なら継続してこの経路を使える。未来候補が残る層では従来の保持処理を使う。
専用経路の展開中に`step>1`が登録されても、その親を残して次世代へ引き継ぐ。
新しいAction・入退場イベントの出力領域は層の先頭でまとめて確保し、件数を別に管理する。
巡回中は添字で書き込み、層の最後に実際の件数へ縮める。通常経路・専用経路の両方で使い、
辺ごとの配列追加に伴う容量確認や長さ変更を減らす。
親別の候補整理には配列の候補リストを使う。`head[parent+1]`に先頭候補番号+1、
`next[slot]`に次の候補番号+1を保持し、0を空とする。選出候補をスロット逆順で
先頭追加するため、同じ親の子は従来どおりスロット昇順で展開する。
親の展開時に`head`を0へ戻し、確保済みの親領域は全消去・累積和をせず再利用する。
待機候補がない専用経路・待機経路を保持する通常経路の両方で同じ整理を使う。
skipBeamやtourBeamと同点処理・展開順は一致せず、得点や選抜件数が変わる場合がある。

## 編集箇所とAPI

`State`（`isFinished: bool`を含む）、`Action`、`evaluate`、`getHash`、`moveForward`、`moveBackward`、`expand`を定義する。
編集用テンプレートの評価値とHashは既定で`state.score`と`state.hash`を参照する。
Actionには適用と巻き戻しに必要な情報を持たせる。複数世代の操作を1つのActionにまとめてよい。

```nim
proc expand(s: var State, f: var SkipTourBeamFrontier[Action, int, uint64]) =
    # TODO: 合法なActionと、その操作が消費する世代数を列挙する。
    for action in legalActions(s):
        s.pushCandidate(f, action, step = action.consumedTurns)

defineSkipTourBeam(search, State, Action, int, uint64)
let answer = search(initial, beamWidth = 1000, maxTurns = 2000)
for action in answer.actions:
    state.moveForward(action)
```

- `pushCandidate(state, frontier, action, step = 1, group = -1)`：仮適用して評価・必要時のHash取得・巻き戻しを行い登録する。
- `frontier.push(action, score, key, finished = false, step = 1, group = -1)`：遷移後の評価値・Hashで直接登録する。
- `frontier.canImprove(score, step = 1, finished = false, group = -1)`：Hash計算前に足切りする。
- `frontier.remainingTurns()`：展開中の状態から世代上限までの残りを返す。
- `search(initial, beamWidth, maxTurns = 2000, minimize = true, groupLimit = 0, groupCount = 0)`：探索を行う。

`step`は正の消費世代数。上限を超える候補は登録しない。世代ごとの選抜器で独立にHash重複を除き、同じHashなら良い評価の候補へ置き換えられる。
親は展開中の位置から自動設定する。Hashには将来の遷移に影響する情報を反映する。整数Hashは再ハッシュせず使用するため、差分ZobristHashを推奨する。
`Key`には`uint64`を指定する。

`groupLimit > 0`では`beamWidth`による全体上限の代わりに、各グループ最大`groupLimit`件を選ぶ。
`groupCount`はグループ数。ID順に安定ソート・Hash重複除去を行い、先のグループを優先する。
重複除去には既存の配列Hash表を再利用し、使用済みビットだけを消去する。
`uint64`のZobristHashは再ハッシュせず使用し、0も有効なキーとして扱う。

## 任意の葉情報

`moveForward` / `moveBackward`は`pushCandidate`で候補を試算して戻す処理で、
盤面・評価値・Hash・補助情報・終了フラグを全て更新・復元する。Forwardは最終Action列の再生にも使う。
`moveBoardForward` / `moveBoardBackward`は、到着して選ばれた候補へ共通祖先経由で移動する処理。
盤面・巻き戻し履歴・終了フラグは更新し、`loadLeaf`で復元する値の更新だけを省ける。
候補への移動が終わると「`loadLeaf`で保存値を上書き → `expand`」の順で呼ばれる。
まずはBoard付きも通常の遷移を呼ぶ実装でよい。Board付きの2関数を定義しない場合も通常の遷移で巡回する。

`SkipTourBeamFrontier[Action, Score, Key, LeafData]`と
`runSkipTourBeam[State, Action, Score, Key, LeafData]`で任意型の保存情報を追加できる。
`defineSkipTourBeam(search, State, Action, Score, Key, LeafData)`も同じ指定に対応する。
選抜用の評価値・Hashとは別に、実コスト・補助評価値・集計値などを保持できる。

```nim
type LeafData = object
    score, moves: int

template getLeaf(s: State): LeafData = LeafData(score: s.score, moves: s.moves)
template loadLeaf(s: var State, leaf: LeafData) =
    s.score = leaf.score
    s.moves = leaf.moves

defineSkipTourBeam(search, State, Action, int, uint64, LeafData)
```

`pushCandidate`は仮適用後、評価値の足切りを通過した候補で`getLeaf(state)`を呼び、
巻き戻す前の値を保存する。未来候補も登録時の値を保持し、到着して展開する時に
`frontier.currentLeaf`へ渡す。`loadLeaf(state, data)`があればStateへ復元してから`expand`を呼ぶ。
初期展開は`getLeaf(initial)`を使う。直接登録では
`frontier.push(action, score, key, leaf = data, step = consumedTurns, ...)`で遷移後の値を必ず渡す。
親番号の更新・重複候補の改善・グループ選抜でも、その候補の保存情報を引き継ぐ。

盤面専用の`moveBoardForward`・`moveBoardBackward`を使う場合は、
そこで更新しない保存成分を新形式の`loadLeaf`で必ず復元する。
通常の遷移だけで巡回する場合は`loadLeaf`を省き、`currentLeaf`だけを使ってもよい。
保存情報は候補にだけ持たせ、経路の全辺には追加しない。
ref・seq・stringを含む型も通常代入で扱うが、共有するref/ptrの内容を後から変更しない。
必要なら`getLeaf`で独立したスナップショットを作り、`loadLeaf`も保存値を書き換えない。
保存する型が大きいほど候補のメモリ・コピー量は増える。

型指定を省略すれば従来形式のままで、追加の保存領域や`getLeaf`呼出しは生成しない。
既存の`loadLeaf(state, score, key)`と`currentScore`・`currentHash`もそのまま使える。
[基本例](../src/examples/skip_tour_beam/basic.nim)は、消費世代数とは異なるAction数も葉から復元する。

## 戻り値と注意点

`SkipTourBeamResult[Action, Score]`は`score`、`actions`、`turns`、`status`、`selectedCandidates`を返す。
`turns`は消費世代数の合計で、`actions.len`とは異なる。Action列の復元はライブラリが行う。
空の世代でも将来候補があれば継続する。完了候補は到達世代まで待機し、その世代で最初の完了候補を返す。
`beamMaxTurns`、`beamFinished`、`beamExhausted`で終了理由を区別する。
候補が尽きた場合は、最後に候補が存在した世代の最良Action列を返す。
`selectedCandidates`は各到達世代の選抜件数と完了候補数（最大1）の累計。

初期Stateは値として受け取る。State内部のref/ptr共有領域は必要に応じて独立させる。
`expand`はStateを元に戻して終了する。Action内の参照先を探索中に変更しない。

祖先を含む保持辺数をE、待機中の全候補数をP、現在世代の選抜件数をWとすると、
世代更新の管理処理はO(E + P + W + D)。Dは現在地や接頭辞のAction数で、世代の最初の移動時に共通祖先を調べる。
これに実際のAction適用・巻き戻し・候補生成・選抜が加わる。
保持辺ごとのID列は追加せず、既存の親番号変換表を再利用する。現在地のAction列・位置列と接頭辞にO(D)の領域を使う。
待機経路が多い場合は配列の走査・コピー量が増えるため、常にskipBeamより高速とは限らない。

## 親別候補整理の計算量と追加比較

保持辺数をE、今回の選出候補数をCとすると、確保済み領域での親別グループ化を
全辺数に依存するO(E+C)からO(C)へ変更した。親の先頭配列は縮めず、拡張部分だけ初期化する。
拡張時には初期化・再確保のコストが加わる。親領域は過去最大の保持辺数に比例する。
Euler巡回・待機候補の親番号更新は残るため、世代更新全体の計算量は変わらない。

AHC041・幅4096の公式入力3件×3反復を計測付きビルドで確認すると、
E/Cは層ごとの中央値8.32、90百分位16.23、最大30.43、総辺数/総候補数は9.51だった。
全8991回は待機候補なしの専用経路を使った。親別整理の時間は探索全体の約15.2%から約0.7%へ減った。
これは計測付きビルド内での割合であり、通常ビルドの改善率とは分けて扱う。

計測処理を入れないreleaseビルドを各3入力×3反復で交互に実行し、
入力ごとの中央値を平均した。基準はc217e5aで、変更は親別候補リストだけ。

| 問題 | 幅 | 変更前 | 変更後 | 時間の変化 |
| --- | ---: | ---: | ---: | ---: |
| AHC041 | 4096 | 1.2264秒 | 1.0228秒 | -16.6% |
| AHC073 | 2816 | 1.6437秒 | 1.6464秒 | +0.2% |
| AHC021・step1/2 | 1536 | 1.5989秒 | 1.5346秒 | -4.0% |

全54出力が公式判定を通過し、旧新版の出力・得点・採用件数・終了ターンが一致した。
別のdebug比較18出力では展開順digestも一致した。AHC073の改善は確認できなかった。
3入力の少数測定であり、他の入力・環境での改善率を保証するものではない。

## 検証

独立したStateコピー・線形選抜の参照実装と、ランダムDAG 200個×評価方向2通り×幅5通り×グループ上限3通りの6,000条件を比較する。
評価・正確なAction列・到達世代・終了理由・選抜件数を照合し、復元したAction列も再生する。
空の世代、stepによる上限超過、将来世代の完了、候補枯渇、初期完了、500世代のref型Actionも確認する。
根から60世代先への待機候補を残すテストでは、2世代ずつ進む候補を選び、展開間の巻き戻し0回を確認する。
2本の枝を維持するテストでは、各世代の展開順が1→2、2→1と反転することを確認する。
テスト・測定スクリプト・生データはローカル専用。

## skipBeamとの速度比較

以下は、世代末に根へ戻っていた変更前のskipTourBeamの測定値。現在地の持ち越し・逆向き巡回を導入した後の値は別に記録する。

[AHC021](https://atcoder.jp/contests/ahc021/tasks/ahc021_a?lang=en)の公式配布入力0000〜0004を使用した。
既存サンプルと同じAction・評価・Hash・1手／2手の遷移を使い、両方式とも固定幅・最大2,000世代とした。
時間による打ち切り・可変幅を無効にし、入力ごとに各3回、実行順を交互に変えて測定した。
時間は探索呼び出しのみを対象とし、起動・入力・出力・公式採点を含めない。
各入力の中央値を取り、その5入力平均を表に示す。

| 問題・条件 | skipBeam | skipTourBeam | 時間比 |
| --- | ---: | ---: | ---: |
| AHC021・幅128 | 128.13 ms | 159.02 ms | 1.241 |
| AHC021・幅1536 | 1.7166 s | 1.7965 s | 1.047 |
| 人工問題・幅512・最大step2 | 28.45 ms | 38.01 ms | 1.336 |
| 人工問題・幅512・最大step4 | 33.47 ms | 49.60 ms | 1.482 |
| 人工問題・幅512・最大step8 | 31.86 ms | 60.85 ms | 1.910 |
| 人工問題・幅4096・最大step2 | 392.16 ms | 383.79 ms | 0.979 |
| 人工問題・幅4096・最大step4 | 486.03 ms | 460.82 ms | 0.948 |
| 人工問題・幅4096・最大step8 | 550.13 ms | 595.38 ms | 1.082 |

AHC021は幅128で約24.1%、幅1536で約4.7%遅かった。
入力・反復をペアにして再標本化した時間比の95%区間は、それぞれ1.192〜1.347、1.004〜1.096。
平均スコアは幅128でskipBeam 90,890／skipTourBeam 90,881、幅1536で91,030／91,075だった。
同点処理・巡回順により選ぶ状態と探索量も変わるため、この比較だけでは管理処理の速度を分離できない。
全60実行について公式採点器で合法性と得点を確認した。公式採点器による再生は実行時間制限の確認を含まない。

人工問題は128世代、1状態あたり6候補、5seed×各3回で比較した。
最大stepを1・2・4・8、幅を512・4096として、全240実行でAction列・評価値・到達世代・選抜件数・展開件数が方式間で一致した。
これにより、同じ状態集合を探索した場合の時間も比較している。
幅4096の最大step2・4では平均時間が短かったが、時間比の95%区間はそれぞれ0.755〜1.007、0.866〜1.039で、明確な優位は確認できなかった。
このAHC021・人工問題の比較だけではskipBeamを速度面で置き換える根拠はなく、独立した選択肢として保持する。

待機経路を連続配列で処理できる一方、印付け・祖先への伝播・配列圧縮・親番号変換の走査が毎世代必要になる。
これらは実装上追加した処理であり、遅さの内訳を特定するには別の計測が必要。
ソース・バイナリ・入力・出力のSHA-256と生データはローカルに保存した。

### AHC041での追加比較

以前tourBeamとの差が大きかったAHC041についても、公式配布入力0000〜0004で比較する。
固定幅128・4096、各入力3回とし、実行順を変えて、入力ごとの中央値の5入力平均を取る。
時間は以前の比較と同じsolve全体で、起動・入力準備・標準出力・採点を含めない。
Stateは8,024バイト、Actionは全方式8バイト。時間による打ち切り・幅調整は無効にする。

- 1ターン遷移：既存AHC041サンプルと同じ遷移・評価・Hashを使い、skipBeam・skipTourBeam・現在の一括コピー採用済みtourBeamを比較する。
- 最大2ターン遷移：全ての1頂点追加候補に加え、それぞれの直後に次の頂点を貪欲に追加する2頂点分のActionを登録する。skipBeam・skipTourBeamで同じ候補生成を使う。

2頂点分のActionは親番号2つを整数に詰め、`step = 2`で登録する。2番目の頂点は、選べる親のうち最も深くなる親を採用する。
これはスキップ動作を実問題で比較するためのローカル実験で、既存AHC041サンプルやライブラリ本体は変更しない。
候補集合が異なるため、最大step1と2の得点差をライブラリの改善とは扱わない。

| 条件 | skipBeam | skipTourBeam | tourBeam（1ターン専用） |
| --- | ---: | ---: | ---: |
| 最大step1・幅128 | 59.65 ms | 82.24 ms | 24.93 ms |
| 最大step1・幅4096 | 3.6239 s | 2.2093 s | 0.7845 s |
| 最大step2・幅128 | 66.29 ms | 92.16 ms | 対象外 |
| 最大step2・幅4096 | 3.6962 s | 2.7761 s | 対象外 |

幅4096ではskipTourBeamがskipBeamより、最大step1で約39.0%、最大step2で約24.9%短かった。
どちらも5入力全てで短く、ペアの入力・反復を再標本化した時間比の95%区間はそれぞれ0.488〜0.727、0.660〜0.932だった。
幅128では逆に約37.9%・39.0%遅かった。1ターン遷移では専用のtourBeamが最速だった。
これは同一環境で測り直した値で、以前の測定値とは混ぜていない。
固定幅の比較なので、表中の2秒を超える実行も計測対象に含めている。

## Stateの完了フラグ

編集用テンプレートは`State.isFinished: bool`を持つ。完了判定用の関数は不要。
初期Stateにも正しい値を設定し、固定ターン探索ならfalseのままにする。
通常beamは`expand`で遷移先の`next.isFinished`を設定してから登録する。
差分更新型の`pushCandidate`は仮適用後の値を読むため、`moveForward`で更新し、
`moveBackward`で以前の値を復元する。展開前のStateのフラグを使い回さない。

```nim
# moveForward内：遷移先の完了状態を保持する
self.isFinished = goalCondition
# moveBackward内では、変更前のisFinishedも復元する
```

`expand`内で評価値・キー・完了判定をまとめて計算する場合は、既存の`push`へ
`finished = goalCondition`を直接渡してもよい（通常beamでは遷移後Stateも渡す）。
初期状態の完了判定にはState側のフラグが必要。
`State`には実在する`isFinished: bool`フィールドが必須。
旧`proc/template isFinished(state): bool`形式は受け付けない。
フラグが将来の動作を区別する情報なら、同一キーで異なる状態を混ぜないようにする。

## 葉の評価値・Hash

通常選抜で同じHashの候補が改善された場合は、変更スロットが更新前の部分木最悪でない
階層から上のセグ木更新を省く。改善によってその部分木の最悪は変わらないためで、
「更新後のindexが同じ」だけを理由には止めない。新規候補との置換は根まで更新する。

採用候補の生値を保持し、`expand`直前に`frontier.currentScore`・
`frontier.currentHash`へ渡す。初期値は`evaluate(initial)`・`getHash(initial)`。
`getHash`は直接`push`する実装でも必要となる。

巡回だけを軽くする場合は`moveBoardForward`・`moveBoardBackward`で盤面・
巻き戻し履歴・`isFinished`だけを更新し、`loadLeaf(state, leafScore, leafKey)`で
評価値・Hashを復元する。この3つはセットで実装する。
盤面フックを省略した場合は従来の`moveForward`・`moveBackward`を使う。
`pushCandidate`の一時評価と最終Action列の再生には通常の遷移を使う。
評価値がStateの保持値と異なる場合は`loadLeaf`で逆変換する。
生値だけから復元できない成分は盤面フックでも更新する。

巡回中の評価用フィールドは古い値なので、盤面フックから参照しない。
`expand`は候補を作るたびに盤面・評価値・Hashを元へ戻す。
