# Tour Beam Search

[編集用テンプレート](../src/lib/search/tour_beam.nim) / [探索エンジン](../src/lib/search/tour_beam_core.nim) / [基本例](../src/examples/tour_beam/basic.nim) / [AHC073例](../src/examples/tour_beam/ahc073.nim)

rhoo版の[木上のビームサーチ：高速化編](https://trap.jp/post/2920/)と参考コードの経路配列方式を参考にした、1ターン遷移専用の差分更新ビームサーチ。
Stateを1つ保持し、採用した候補の親へ移動して展開する。親・子・兄弟リンクやObjectPoolは使わない。
`trace`に現在の経路、`tour`に別の葉へ移るための経路断片、`leaves`にその境界を保持する。
共通祖先まで巻き戻して必要な差分だけ適用し、次の層に必要な経路配列を作る。
候補は親の葉番号で計数整列するため、巡回順を作る全体ソートは行わない。
経路断片は`supportsCopyMem(Action)`がtrueなら`copyMem`で一括コピーする。
ref・seq・stringなどを含み参照管理が必要なActionは、通常の要素代入へコンパイル時に切り替える。

## 編集箇所

- `State`・`Action`を定義し、初期評価値とHashを設定する。
- `evaluate`は既定で`state.score`、`getHash`は`state.hash`を返す。
- `moveForward`でActionを適用し、評価値・Hash・補助情報を差分更新する。
- `moveBackward`で対応する変更を完全に元へ戻す。
- `expand(state, frontier)`で合法なActionを列挙し、`state.pushCandidate(frontier, action)`で登録する。
- `isFinished`で途中完了を判定する。固定ターンの最終層で比較する場合は常にfalseでよい。

Actionは、適用元のStateからいつでも再適用・巻き戻しできる情報を持たせる。
変更前の値やXOR差分などもActionに保存する。Stateを共有するref/ptrをActionに持たせて書き換えない。
`expand`は終了時にStateを元へ戻す。ヘルパーの`pushCandidate`は仮適用・評価・必要時のHash取得・巻き戻しを行う。
初期Stateは値としてコピーするため、ref/ptrの共有領域は必要に応じて呼び出し前に独立させる。

## 呼び出し

```nim
defineTourBeam(tourBeam, State, Action, int, uint64)
let answer = tourBeam(initial, beamWidth = 1000, maxTurns = 100)
echo answer.score
echo answer.actions
```

汎用の入口は`runTourBeam[State, Action, Score, Key]`。
フロンティアは`TourBeamFrontier[Action, Score, Key]`、結果は`TourBeamResult[Action, Score]`。
編集用テンプレートは型を固定済みなので、そのまま`tourBeam(initial, ...)`を呼ぶ。

| 引数 | 既定値 | 意味 |
| --- | --- | --- |
| `beamWidth` | 必須 | 各層に残す候補数の上限 |
| `maxTurns` | `2000` | 探索する層数の上限。1Actionは必ず1層進む |
| `minimize` | `true` | falseなら評価値を最大化 |
| `groupLimit` | `0` | 正なら各グループに残す候補数の上限 |
| `groupCount` | `0` | グループ数。IDは`0..<groupCount` |

時間計測・可変幅・`step`は持たない。複数ターン後へ飛ぶ遷移には[skipBeam](skip_beam.md)を使う。
coreは`header.nim`を読み込むが、通常ビームやskipBeamには依存しない。

## 候補選抜と結果

`frontier.push(action, score, key, finished = false, group = -1)`で評価済みの候補も直接登録できる。
親は展開位置から自動設定する。`score`・`key`・`finished`は遷移後の値を渡す。
`frontier.canImprove(score, finished = false, group = -1)`でHash計算前に足切りできる。
`frontier.remainingTurns()`は現在位置から残されたターン数を返す。

通常選抜はindexのみのセグ木を幅到達時に構築し、最悪候補を置換する。
Hash一致は同一状態として扱い、後から来た評価の良い候補でActionと親も置換する。
同点・悪化は置換しない。異なるHash値のHash表上の衝突は線形探索で区別する。
セグ木・Hash表・候補配列・経路用バッファは層をまたいで再利用する。

`groupLimit > 0`では候補登録時に`group`を渡す。
グループID順に安定ソートで上位候補を選び、同じHashの重複を除く。
同点は登録順、グループをまたぐ重複は先に処理したグループを優先する。
全体の`beamWidth`は使わず、最大`groupCount * groupLimit`件を保持する。
この方式の`push`成功は選抜までの保留を意味し、最終採用を保証しない。

通常選抜の登録はHash表の期待償却O(1)とセグ木のO(log W)。
巡回順の計数整列はO(W + 前層の葉数)、状態遷移の回数は保持した経路の分岐形状による。
深さDまでの経路配列は最悪O(WD)、これに幅Wの候補・選抜器とState1つを保持する。
グループ方式では、選抜まで保留する全候補とそのソート領域も必要になる。

結果の`actions`は初期Stateからの適用順。過去の全候補を保存せず、終了時に経路配列から復元する。
最終Stateは返さないので、必要ならAction列を初期Stateへ再生する。
`turns == actions.len`となり、`selectedCandidates`は各層の採用未完了候補数と完了候補数（最大1）の累計。

- `beamFinished`：初期完了、または最初に登録された完了候補に到達。
- `beamMaxTurns`：最終層の最良候補を返す。`maxTurns = 0`なら初期評価値と空の行動列。
- `beamExhausted`：次候補がなくなった場合に、直前の層の最良候補を返す。

展開順は経路配列の巡回に従うため、通常ビーム・skipBeamと同点候補や先着完了解の選択が異なることがある。
引数は`beamWidth > 0`、`maxTurns >= 0`、有効なグループIDを渡す。引数検査は`-d:debug`時に行う。

## AHC073例

通常ビームの[共通問題処理](../src/examples/beam_search/ahc073_problem.nim)を使い、
後ろの目的地から1区間ずつ決める。評価式・40通りの経路列挙・最終出力を共通化している。
Actionは魔法陣位置のXOR差分45bit・コスト10bit・経路ID6bitをuint64へ格納し、
別のuint64にZobristHashのXOR差分を保持する。Actionは計16バイト。
同じ位置の魔法陣が複数ある場合も、個数ごとに異なるZobrist値を使って多重集合を区別する。
StateにHashを保持し、経路の適用・巻き戻しではその差分だけを反映する。
探索後に復元したActionを再生し、共通の出力処理へ経路IDと最終Stateを渡す。

```sh
nim cpp -d:release -o:build/ahc073_tour src/examples/tour_beam/ahc073.nim
./build/ahc073_tour < in.txt > out.txt
```

既定幅は64。`-d:Ahc073BeamWidth=2816`などで変更できる。
これは評価関数による近似探索であり、方式を変えても同じスコアや同じ出力になるとは限らない。

## 検証・速度比較

独立したStateコピー参照と、ランダムDAG 150個×評価方向2通り×幅5通り×グループ上限3通りの
4,500条件で、評価値・Action列・終了理由・深さ・選抜件数を照合した。
別途500層の共通経路・分岐、ref型Actionと文字列Hash、Hash表上の衝突を検証する。
AHC073のAction適用・巻き戻し・Zobrist差分は、盤面サイズ2〜128の24,000遷移で確認する。
debug/releaseの関連11チェックと、通常ビームの既存16チェックが通過した。
共通問題処理へ分離した通常版の比較用13出力も、変更前と一致した。

AHC073のtourBeam例は幅64で公式再生100/100件が完了し、平均スコア7,832.53。
通常版の7,833.05とは巡回順による候補選択差がある。debug/releaseの10入力は全出力が一致した。

### AHC073の差分更新版での追加比較

同じ評価・差分ZobristHash・16バイトActionで、次の2案をローカルに実装した。

## Stateの完了フラグ

編集用テンプレートは`State.isFinished: bool`を持つ。完了判定用の関数は不要。
初期Stateにも正しい値を設定し、固定ターン探索ならfalseのままにする。
通常beamは`expand`で遷移先の`next.isFinished`を設定してから登録する。
差分更新型の`pushCandidate`は仮適用後の値を読むため、`moveForward`で更新し、
`moveBackward`で以前の値を復元する。展開前のStateのフラグを使い回さない。

```nim
# moveForward内：遷移先の完了状態を保持する
self.isFinished = goalCondition
# moveBackward内では、変更前のisFinishedも復元する
```

`expand`内で評価値・キー・完了判定をまとめて計算する場合は、既存の`push`へ
`finished = goalCondition`を直接渡してもよい（通常beamでは遷移後Stateも渡す）。
初期状態の完了判定にはState側のフラグが必要。
`State`には実在する`isFinished: bool`フィールドが必須。
旧`proc/template isFinished(state): bool`形式は受け付けない。
フラグが将来の動作を区別する情報なら、同一キーで異なる状態を混ぜないようにする。
